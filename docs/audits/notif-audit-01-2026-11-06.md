## 0. Synthèse pour le CTO

1. **Un P0 inter-utilisateur (P0-01, ex-A10)**, confirmé au niveau du service mais pas encore par
   l'API : dans un même établissement, un compte disposant de `Notifications:UPDATE` (par défaut
   SCHOOL_ADMIN, PROVISEUR, PRINCIPAL, PREFET_ETUDES, SECRETARY) peut lire par identifiant une
   notification adressée à un autre utilisateur, par exemple « {élève} a été signalé(e) absent(e) »
   destinée à un parent. **Aucune faille inter-établissement** : école imposée par le JWT,
   participation active exigée pour lire un message, cible de navigation vérifiée pour
   l'établissement, accès plateforme (Superadmin / Admin Pays) refusé.
2. **Web : navigation conforme pour les 9 types de cible**, mais au niveau de la conversation, pas du
   message (aucun `messageId` n'est transporté).
3. **Push Android : seuls 3 types sur 10 ouvrent la bonne ressource** (message → conversation,
   annonce → détail, échéance → paiements de l'élève). Absence, retard, note, bulletin, paiement
   reçu, emploi du temps, remplacement et notification manuelle ouvrent **l'accueil** (P1, prouvé par
   sonde).
4. **Le centre de notifications Mobile** refuse d'ouvrir ces 6 types métier (« Ouverture impossible »)
   alors que le Web les ouvre (P1).
5. **Push iOS : absent.** Le backend rejette l'enregistrement d'un appareil iOS (`400 PUSH-N1 : Android
   uniquement`) et le Mobile n'enregistre pas de jeton hors Android (P1).
6. **Suppression de message : absente partout** (aucune route, aucune colonne, aucun écran) (P1).
   Le retrait d'une notification existe déjà : c'est un **archivage par destinataire**, sans effet sur la
   ressource d'origine (conforme).
7. **L'aperçu Push d'un message est générique** (« Nouveau message » / « Vous avez reçu un nouveau
   message. »), sans expéditeur ni extrait, alors que le nom de l'élève apparaît pour les absences et
   paiements (P2 ; cible fixée par ARB-1).
8. **L'état lu n'est pas relié entre domaines** : lire la conversation ne marque pas la notification
   « Nouveau message » comme lue, et toucher un Push ne la marque pas non plus (P2).
9. **Un Push peut être perdu sans relance** si le traitement s'interrompt entre la création de la
   notification et la création de ses envois (P2).

## 1. Cartographie de l'architecture actuelle [FAIT]

```
Écriture métier (school_messages, announcements, attendance, grades, report_cards,
                 payments, course_schedule_weekly_slots, remplacements, échéances)
   │ triggers PL/pgSQL somafrik_enqueue_communication_event()      (+ sweep échéances, + manuel)
   ▼
communication_event_outbox  (event_key UNIQUE, status pending/processing/processed/failed)
   │ communicationsNotificationsWorker.runOnce (toutes les 5 s)
   │   └ drainOutbox → processOneEvent → eventSpec() : titre, corps, navigation_target, destinataires
   ▼
communication_notifications (1 par event_key)  +  notification_recipients (read_at, archived_at par user)
   │ dispatchProcessedEvents → communicationChannelFanout
   │   └ politique école (school_notification_settings) × préférences user × catégorie destinataire
   ▼
communication_channel_deliveries (delivery_key event:user:channel UNIQUE, 8 tentatives, dead_letter)
   │ dispatchPush → mobile_push_devices (user + school + APP_ENV, non révoqués)
   ▼
Expo Push API (expoPushService) → tickets → mobile_push_receipts (vérifiés ~15 min plus tard)
```

Lecture côté client :

- **Web** : `/notifications` (InternalNotificationsCenter) → bouton « Ouvrir » →
  `resolveNotificationDestination()` → route `?<id>=` → la page cible lit l'identifiant
  (`useDeepLinkId`) et sélectionne la ressource.
- **Mobile** : Push → `PushNotificationsRuntime` → `resolvePushNavigationData()` (liste blanche de
  5 destinations) → `navigationRef.navigate`. Centre in-app : `InternalNotificationsScreen` →
  `resolveInternalNotificationNavigationTarget()` (3 types).

Trois états de lecture distincts, tous en PostgreSQL :

| Domaine | Table | Écrit par |
|---|---|---|
| Message | `school_message_reads (message_id, user_id)` | `PATCH /messages/:id/read` |
| Annonce | `announcement_reads (announcement_id, user_id)` | `PATCH /announcements/:id/read` |
| Notification | `notification_recipients.read_at / archived_at` | `PATCH /internal-notifications/:id/read · /archive` |

Aucun lien n'existe entre ces trois états (voir A07).

## 5. Anomalies

### P0 — Critique

#### P0-01 (ex-A10) — Lecture d'une notification privée d'un autre utilisateur par un gestionnaire d'établissement

Reclassée P0 en application de la règle CTO : toute faille inter-utilisateur confirmée donnant accès à
une notification privée sans autorisation.

| Champ | Contenu |
|---|---|
| Description | Un utilisateur qui **n'est pas destinataire** d'une notification, mais dispose de `Notifications:UPDATE`, obtient son titre, son corps et sa cible de navigation via `GET /api/backoffice/internal-notifications/:notificationId` |
| Sévérité | **P0** (inter-utilisateur, même établissement). Pas de franchissement d'établissement : la requête impose `n.school_id = <école du JWT>` |
| Plateforme | Backend → Web et Mobile (même API) |
| Fichier · fonction | `backend/lib/communicationsNotificationsService.js` : `canManage` (ligne 81), `loadVisible` (lignes 201-215, paramètre `management`), `get` (appel avec `canManage(principal)`) ; même schéma dans `downloadAttachment` (`!recipient && !canManage(principal)`) pour les pièces jointes des notifications manuelles |
| Rôles concernés | Grants système par défaut, `notifications` avec `can_update = true` : SCHOOL_ADMIN, PROVISEUR, PRINCIPAL, PREFET_ETUDES, SECRETARY (`backend/db/migrations/20260903_p0_system_roles_rbac_reconciliation.sql`, lignes 894, 918, 942, 966, 989). TEACHER, PARENT et STUDENT : lecture seule, non concernés |
| Données exposées | Notifications d'absence et de paiement : **nom de l'élève** ; notifications manuelles ciblées et leurs pièces jointes ; identifiants de l'élève et de la ressource. Notifications de message : corps générique, et le contenu du message reste protégé par le contrôle de participation |
| Cause | Contournement « gestionnaire » de la vérification destinataire, conçu pour l'auteur d'une notification manuelle mais appliqué à toutes les notifications |
| Conditions | Connaître l'identifiant (UUID) de la notification : la liste ne l'expose pas, puisque `list` joint `notification_recipients` sur l'utilisateur connecté. Les UUID peuvent toutefois fuiter (journaux, captures, URL partagées, réponse de `POST` pour l'auteur) |
| Ce qui reste protégé | `markRead` et `archive` exigent une ligne destinataire (`UPDATE … WHERE user_id = $2 AND school_id = $3`). Un non-gestionnaire reçoit 404 |
| Preuve | **[FAIT, niveau service]** Sonde exécutée hors dépôt : appel direct de `get()` avec un store simulé, le lecteur n'étant pas dans `notification_recipients`. Avec `Notifications:UPDATE` → **notification retournée** (`"Awa Diallo a été signalé(e) absent(e)."`). Sans cette permission → **404 « Notification introuvable. »**. Ce n'est ni un test HTTP ni un test PostgreSQL |

## 6. Analyse RBAC et multi-tenant [FAIT sauf mention]

- **Tenant** : l'école provient uniquement du JWT (`resolveWritableSchoolCode`) ; le `schoolCode` du
  client est ignoré (COM-C1).
- **Destinataire** : lecture, marquage lu et archivage d'une notification filtrés par `user_id` et
  `school_id` (sauf P0-01 pour la lecture du détail). Messages : participation active obligatoire (`requireActiveParticipant`).
  Annonces : destinataire de l'instantané `announcement_recipients`, ou gestionnaire.
- **Cible de navigation** : `sanitizeNavigationTargets` vide la cible si une ressource existe dans un
  autre établissement ; une ressource supprimée laisse une cible inerte.
- **Superadmin / Admin Pays** : refusés sur la messagerie et les notifications d'établissement
  (`PLATFORM_PERSONAL_DATA_DENY`) ; le Web les envoie vers `/notifications-plateforme`.
- **Multi-rôle** (enseignant et parent) : les catégories de destinataire sont calculées sur l'ensemble des
  rôles de l'utilisateur (`resolveUserRecipientCategories`), sans filtre par rôle actif. La notification
  reste visible quel que soit le rôle choisi. L'accès effectif reste contrôlé par l'API de la ressource
  [HYPOTHÈSE : comportement par rôle actif non testé].
- **Parent de plusieurs enfants** : `constrainParentPushNavigation` renvoie vers l'accueil si l'élève du
  Push n'est pas lié au parent.
- **Révocation** : les destinataires sont figés au moment du traitement de l'événement. Après la
  révocation d'un rôle, une ancienne notification reste listée, mais la ressource est refusée par son API.
  Une notification « Nouveau message » d'un participant retiré reste visible, avec un corps générique
  [HYPOTHÈSE à confirmer par TEST-14].
- **Jetons** : un téléphone partagé par deux comptes ne garde que le dernier compte connecté. Une session
  expirée sans déconnexion laisse le jeton actif ; les Push continuent, puis la connexion est exigée avant
  la navigation (`flushPendingPushNavigation`).

## 9. Architecture cible proposée (réutilise l'existant) [RECO]

1. **Un seul contrat de cible** : la table `TARGET_RESOURCES` (backend) reste la référence. On y ajoute
   `messageId` pour `conversation`. Le Push transporte `notificationId`, `schoolCode`, `type` et les
   identifiants de la cible, au lieu de `somafrikDestination` codé en dur par type.
2. **Un seul résolveur Mobile**, partagé entre Push et centre in-app, qui traduit la cible vers les
   **écrans existants** (`Messages`, `Announcements`, `StudentPayments`, `StudentNotes`,
   `StudentPresences`, `ReportCards`, `Timetable`). Aucun nouvel écran sans validation CTO.
3. **Lecture couplée côté serveur** : lire la source marque lues les notifications du même
   destinataire dont la source correspond (`source_entity_id` = message ou annonce, même `user_id` et
   `school_id`). Le clic Push appelle `PATCH …/internal-notifications/:id/read`.
4. **Suppression par participant** : masquage par participant (table dédiée ou colonne sur
   `school_message_reads`, **migration à valider**), filtré dans la liste des messages, les compteurs et
   le dernier message ; jamais de `DELETE` physique par défaut.
5. **Fiabilité** : balayage de rattrapage des envois manquants, plafond de tentatives sur l'outbox.
6. **Aperçu** : politique d'aperçu par type d'événement, décidée par le CTO (A06).
